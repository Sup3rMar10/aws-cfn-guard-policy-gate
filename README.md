# aws-cfn-guard-policy-gate

![ci](https://github.com/Sup3rMar10/aws-cfn-guard-policy-gate/actions/workflows/ci.yml/badge.svg)

**Policy-as-code for CloudFormation, with the policies themselves tested.** Twelve [cfn-guard](https://github.com/aws-cloudformation/cloudformation-guard) rules (S3, security groups, IAM, RDS, EBS, KMS, logs, tags) plus the part most policy repos skip: proof that each rule actually *catches* what it claims, and does not flag what it should leave alone.

> **What is verified, and what is not.** Locally with cfn-guard 3.2.1: **28 native unit-test cases pass**, and a matrix of **every rule against 27 fixture templates** (25 deliberately non-compliant, 2 compliant) returns exactly the expected failures. I weakened two rules on purpose and both test layers failed. `cfn-lint` passes on the compliant templates, and GitHub Actions on Linux passed the unit tests and the full matrix with cfn-guard 3.2.1 pinned (2026-10-17). **No AWS account is involved**: this checks template *text*, so it says nothing about what is actually deployed.

## The rules (`rules/`)

| File | Rules |
|---|---|
| `s3.guard` | bucket encrypted; all four public-access blocks on; versioning enabled |
| `network.guard` | no SSH (22) or RDP (3389) open to the world, including **inside a port range** (20-25) and **"all traffic"** (`-1`), over IPv4 and IPv6, inline or as a standalone ingress rule |
| `iam.guard` | no `Allow` of `Action: *` on `Resource: *`, for managed policies and for a role's inline policies, as strings or as lists |
| `data.guard` | RDS encrypted, not public, at least 7 days of backups; EBS encrypted; KMS rotation; log groups have retention |
| `tags.guard` | data-holding resources carry `Owner` and `Environment` tags |

## Why the policies are tested (and what that found)

A policy that never fails looks identical to a policy that works. So there are two test layers:

1. **`unit.sh`**: cfn-guard's native `test` command, one file per rule file, 28 cases (`tests/rule-tests/`).
2. **`matrix.sh`**: runs *all* rules against *every* fixture and requires the failing set to match `templates/bad/expected.json` **exactly**: a missed violation fails the matrix, and so does a rule that flags something extra. Compliant edge cases must produce zero failures: world-open HTTPS, SSH from a private range, `Allow s3:*` on one bucket, `logs:Get*` on `*`, a `Deny` of `*` on `*`.

Building them found **three real bugs in my own rules**, each a false negative that would have passed bad templates:

- **A filter that never matched.** `%dbs.Properties[ PubliclyAccessible exists ] { ... }` evaluated to SKIP, so a *publicly accessible database passed*. Rewritten as `PubliclyAccessible !exists or PubliclyAccessible == false`.
- **A second filter that never matched** (standalone security-group ingress), same symptom, same fix (`when CidrIp == ... { }`).
- **"One good bucket hides a bad one".** The flat form `%buckets.Properties.X == ...` only evaluates the buckets where `X` resolves, so a template with one encrypted bucket and one with no `BucketEncryption` passed. Every rule is now written per resource (`%buckets { Properties.X ... }`), with a fixture (`two-buckets-one-bad`) and a unit case that fail if anyone flattens it again.

And a bug in the *harness*: a template cfn-guard could not parse reported "no failures", so an unreadable fixture looked compliant. `matrix.sh` now treats any exit code other than 0 (pass) or 19 (violations), and any parse error, as an ERROR. (The unreadable fixture was my own: Python's YAML dumper emitted anchors `&id001` that cfn-guard's parser rejects.)

One behaviour worth knowing: when a rule's filter matches nothing (SSH only from a private range, a `Deny` statement, a role with no inline policies) cfn-guard reports **SKIP**, not PASS. That is the right outcome for "nothing to evaluate", and the unit tests assert it explicitly.

## Honest limits

- **Template text, not reality.** These rules read the CloudFormation you wrote. They cannot see values from parameters, `Fn::If` branches the template resolves at deploy time, nested stacks in other files, resources created outside CloudFormation, or console drift. Combine with runtime checks (AWS Config, Security Hub) for that.
- **Twelve rules is a sample, not a baseline.** Nothing here covers networking beyond SSH/RDP, encryption in transit, IAM `NotAction`/`Resource` patterns, public subnets, or the other 1,000 ways to misconfigure AWS. It is a pattern, not a compliance programme.
- **The IAM rule is narrow on purpose:** it flags only `Allow` of `*` on `*`. `s3:*` on `*`, or `iam:PassRole` on `*`, are dangerous too and are not flagged.
- Rules that read `Properties.X` assume the common shapes. Intrinsic functions in a value (`!If`, `!Ref` to a parameter) are not evaluated, so a value cfn-guard cannot see as a literal may not match the way you expect; I did not test those cases.
- The fixtures were generated by a script I did not keep; they are committed as plain YAML and are the source of truth.
- cfn-guard 3.2.1 on Windows and Linux; other versions may behave differently (notably around SKIP and unresolved queries).

## Use it

```
cfn-guard validate -r rules -d path/to/template.yaml --show-summary fail
bash unit.sh        # test the rules
bash matrix.sh      # test the rules against the fixtures
```

In a pull-request workflow, install a pinned cfn-guard (see `ci.yml`) and run the first command over your changed templates; its exit code is 19 when any rule fails, which fails the job. (That snippet is the pattern used in this repo's own CI, not a tested example for your repository.)
